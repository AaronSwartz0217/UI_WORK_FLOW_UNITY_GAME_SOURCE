# Universal UI AI Processing Standard

## 按钮文字与符号保留硬门槛

- 拆分前必须逐个按钮登记其原始可见内容，包括动作文字、识别文字和功能符号，例如“开始”“最大”“鉴定”“+”“−”“×”“?”。
- 原布局图中已经位于按钮内部、用于识别按钮功能的文字或符号，默认属于按钮视觉本体，必须保留在按钮 PNG 中；不得因为执行“去除普通文字”而删除。
- 只有用户明确要求无字底板，或项目明确规定文字由引擎文本节点独立渲染时，才允许输出无字按钮；此时必须同时交付独立文字资源或文字节点配置，并在清单与 QA 中记录依据。
- Normal、Hover、Pressed、Disabled 四态中的文字内容、字形身份、拼写、对齐和锚点必须一致；状态变化只允许改变亮度、颜色、材质响应、描边或按压反馈。
- 必须生成 `BUTTON_TEXT_MATRIX.md`，逐个按钮登记预期内容、四态检查结果和最终结论。
- 必须在四态并排预览中直接标明预期文字或符号，并执行“原布局图 → Normal → Hover → Pressed → Disabled”的逐项视觉核对。
- 任一按钮原本带字但成品缺字、错字、换字、文字偏移或仅部分状态带字，均判定为 `Fail`；该按钮整组不得进入 `out/Components`。
- QA 不得仅检查 Alpha、尺寸和状态亮度，还必须检查按钮文字、符号的存在性以及跨状态一致性。
# 通用 UI AI 生成、抠图、拆分与交付规范

> 本文档适用于游戏、应用、网页、工具、商城、背包、角色、任务、活动、登录等 UI 项目。  
> 项目专属文档可以补充具体尺寸、路径和组件清单，但不得降低本文的透明度、拆分、命名和 QA 要求。
>
> This standard applies to game, app, web, tool, shop, inventory, character, quest, event, login, and other UI projects.

---

## 1. 目标 / Goal

将白模、原始界面图和风格参考转换为可复用、可交互、可验证的正式 UI 资源，并确保：

- 布局遵循白模或产品设计；
- 风格统一；
- 每个文件职责单一；
- 按钮、图标、文字和结构面板彼此独立；
- 组件外部为真实透明 Alpha；
- 动态内容不烘焙进静态资源；
- 文件名、尺寸、状态和文档一致；
- 后续 AI、程序、美术无需聊天记录即可继续工作。

## 2. 强制目录结构 / Mandatory Folder Structure

每个 UI 任务统一使用三个工作目录：

```text
InterfaceName/
├─ README.md
├─ INTRODUCTION.md
├─ in/
├─ into/
└─ out/
```

目录名固定为小写英文：

```text
in
into
out
```

不得改成 `input`、`intermediate`、`output`、`source`、`production`、中文名称或其他近义词。

### 2.1 `in`：输入、原型和风格参考

`in` 只保存任务开始前已经存在或由用户提供的输入资料：

- 白模图；
- 原型图；
- 线框图；
- 页面布局参考；
- 风格参考图；
- 材质参考图；
- 色彩参考图；
- 用户提供的原始界面截图；
- 配置表和必要的输入说明。

标准示例：

```text
in/
├─ InterfaceName_Wireframe_WidthxHeight.png
├─ InterfaceName_Prototype_WidthxHeight.png
├─ InterfaceName_StyleReference_01_WidthxHeight.jpg
├─ InterfaceName_StyleReference_02_WidthxHeight.png
└─ Config/
```

规则：

- `in` 是只读输入区；
- 不得直接覆盖、裁切或修改其中的原文件；
- AI 开始工作前必须枚举并查看 `in` 中的全部文件；
- 白模与风格参考必须明确区分；
- 用户新提供的输入图必须先归入 `in`。

### 2.2 `into`：中间件和过程图片

`into` 保存所有尚未成为最终交付物的过程文件，例如：

- 完整带字效果图；
- 仍包含按钮和图标的效果模板；
- 已去按钮但尚未去字的中间模板；
- 已去字但仍含按钮的检查模板；
- 键色背景组件图；
- 尚未完成 Alpha 清理的图片；
- 候选状态；
- 对比图；
- 修复候选图；
- 临时重组图；
- 尚未通过 QA 的文件。

标准示例：

```text
into/
├─ InterfaceName_EffectMockup_Default_WidthxHeight.png
├─ InterfaceName_WithButtonsTemplate_Default_WidthxHeight.png
├─ InterfaceName_NoButtonsIconsTemplate_Default_WidthxHeight.png
├─ InterfaceName_NoTextTemplate_Default_WidthxHeight.png
├─ ChromaKey/
├─ Candidates/
└─ ReassemblyPreview/
```

规则：

- `into` 中的文件不是正式资源；
- 游戏、应用、配置和预制体不得引用 `into`；
- 中间文件可以带字、带按钮、带图标或带键色背景，但名称必须明确当前处理阶段；
- 禁止使用 `new`、`final`、`最终版` 等模糊名称；
- 只有通过抠图、命名、透明度和视觉验收后，文件才能进入 `out`；
- 失败候选可以保留用于复盘，但不得与最终结果混放。

### 2.3 `out`：最终结果

`out` 是唯一正式交付目录，包含：

- 最终真透明按钮；
- 最终真透明图标和槽位；
- 最终状态效果；
- 最终结构面板；
- 之前已经抠成功并通过 QA 的模板；
- 无按钮、无图标、无文字的最终纯净透明模板；
- 正式 QA 报告；
- 棋盘格透明预览；
- 必要的最终资源清单。

标准示例：

```text
out/
├─ Components/
│  ├─ InterfaceName_CloseButton_Normal_52x52.png
│  ├─ InterfaceName_CloseButton_Hover_52x52.png
│  ├─ InterfaceName_CloseButton_Pressed_52x52.png
│  ├─ InterfaceName_CloseButton_Disabled_52x52.png
│  └─ InterfaceName_ItemSlotIcon_Default_88x88.png
├─ Templates/
│  └─ InterfaceName_CleanTemplate_Empty_WidthxHeight.png
└─ QA/
   ├─ FINAL_QA.md
   └─ TRUE_ALPHA_CHECKERBOARD.png
```

规则：

- `out` 中一个用途只能存在一个当前正式版本，状态资源除外；
- 每张组件 PNG 只能包含一个完整组件；
- 组件外部必须为真实透明 Alpha；
- 按钮状态组必须整体通过后才能进入 `out`；缺少必需状态的单张 Normal 只能留在 `into/Candidates`；
- `out` 禁止出现键色背景、截图底色、临时文件和失败候选；
- 最终纯净模板必须放在 `out/Templates`，不能只留在 `into`；
- `out` 中的文件新增、删除、改名或替换后，必须同步 README 和 QA；
- 程序、配置和预制体只能引用 `out` 中的正式资源。

### 2.4 三个目录之间的流转

```text
in
原型、白模、风格参考
    ↓
into
效果图、带字模板、含按钮模板、键色图、候选图
    ↓
out
单组件真透明 PNG、最终纯净模板、正式 QA
```

强制原则：

- 输入资料从 `in` 读取，不在原位修改；
- 过程文件全部写入 `into`；
- 只有完成两轮 QA 的资源才能写入 `out`；
- 不允许绕过 `into`，把未验证生成图直接放入 `out`；
- 不允许把已经进入 `out` 的正式文件重新当作中间件覆盖；
- 旧错误文件移出 `out` 后，可以放入 `into/Rejected`，但不得继续被正式引用。

项目根目录必须使用有意义的英文名称，禁止只使用 `UI`、`New Folder`、日期、人员名或版本号。

### 2.5 项目名称输入与命名标识

每个新 UI 任务开始前必须先确定项目名称。项目名称同时包含：

```text
ProjectDisplayName：用户可读名称，可以使用中文，例如“装备打造”
ProjectId：稳定英文标识，例如 EquipmentCraftingUI
```

如果用户尚未提供名称，必须在生成或创建目录前询问。不得先使用 `UI`、`PanelSplit`、`NewProject`、日期或临时名称，之后再把临时名称当作正式接口。

`ProjectId` 规则：

- 只使用英文字母和数字；
- 使用 PascalCase；
- 必须表达具体业务用途；
- UI 项目默认以 `UI` 结尾；
- 同一项目从开始到交付保持不变；
- 不得包含空格、中文、连字符、人员名、日期、`new`、`final` 或版本号；
- 已存在项目重命名时，必须同步文件夹、组件前缀、文档、清单、配置和引用。

命名示例：

| ProjectDisplayName | ProjectId | 项目文件夹 | 组件示例 |
|---|---|---|---|
| 装备打造 | `EquipmentCraftingUI` | `EquipmentCraftingUI/` | `EquipmentCrafting_CloseButton_Normal_64x64.png` |
| 烹饪模式 | `CookingModeUI` | `CookingModeUI/` | `CookingMode_StartButton_Normal_240x72.png` |
| 装备鉴定 | `EquipmentAppraisalUI` | `EquipmentAppraisalUI/` | `EquipmentAppraisal_MaterialSlot_Empty_96x96.png` |

组件文件名前缀使用去掉末尾 `UI` 的业务标识：

```text
ProjectId: EquipmentCraftingUI
ComponentPrefix: EquipmentCrafting
```

项目名称确认格式：

```text
ProjectDisplayName:
ProjectId:
ComponentPrefix:
```

必须在 README、INTRODUCTION、拆分清单和 QA 中记录这三个字段。

## 3. 输入资料分类 / Input Classification

工作前必须枚举并查看 `in` 中的全部输入文件，记录：

- 文件名；
- 像素尺寸；
- 用途；
- 是否为白模；
- 是否为风格参考；
- 是否为生成或拆分来源；
- 与其他输入图的关系；
- 是否存在缺失或冲突。

输入图职责：

- 白模图：约束布局、比例、层级和组件位置；
- 风格参考：约束材质、颜色、光影、边框和氛围；
- 原始界面图：作为已有 UI 的拆分来源；
- 完整效果图：作为新 UI 的组件抠图与模板清理来源；
- 配置表、代码和预制体：约束资源路径、名称、状态和引用关系。

不得把风格参考的布局错误套用到白模，也不得把白模的临时颜色当作最终风格。

### 3.1 双参考输入标准 / Layout + Style Reference

新 UI 生成任务默认采用“双参考输入”：

```text
图一：面板排布图 / Layout Reference
图二：视觉风格图 / Style Reference
README：生成、拆分、透明、裁剪、命名与 QA 规则
```

三者职责不得混用：

| 输入 | 决定内容 | 不得决定内容 |
|---|---|---|
| 图一：面板排布图 | 目标画布、宽高比、面板数量、相对位置、尺寸比例、层级、嵌套关系和布局留白 | 最终材质、配色、光影、磨损和装饰风格 |
| 图二：视觉风格图 | 材质、色彩、边框语言、倒角、金属或木材质感、磨损、光影、装饰密度和整体氛围 | 新 UI 的面板数量、位置、尺寸和业务布局 |
| README | 工作顺序、组件分类、选择确认、抠图、Alpha、极限裁剪、命名、重组、文档和 QA | 未经输入支持的业务内容和任意新增布局 |

核心公式：

```text
图一决定：有什么、在哪里、占多大、谁包含谁
图二决定：看起来是什么风格
README 决定：如何生成、拆分、裁剪、命名和验收
```

### 3.2 图一：面板排布图

图一可以是白模、线框图、色块图、手绘框、带位置标注的截图或低保真原型。读取时必须记录：

- 原始画布尺寸和宽高比；
- UI 有效范围，不把截图边缘或设备背景误认为 UI；
- 每个候选区域的矩形范围、中心点和相对比例；
- 区域属于根面板、子面板还是嵌套组件；
- 面板之间的上下左右关系、对齐线、间距、重叠和 Z 轴层级；
- 哪些形状只是标注线、占位色或说明文字；
- 哪些区域必须保持空白，禁止自行加入分栏、槽位、文字或按钮；
- 是否要求保留原画布坐标，或仅交付紧边独立组件。

布局遵循规则：

- 最终结构必须服从图一，不得用图二的布局覆盖图一；
- 图一中空白区域默认保持单一空结构，除非用户或配置明确要求增加内容；
- 不能因为风格图含有标签页、槽位、分栏或按钮，就把这些结构擅自加入图一；
- 标注框可以表示关注区域，但正式边界仍须依据白模轮廓、闭合结构和用户确认确定；
- 图一包含多个区域时，必须执行 `PanelSelectionMode` 确认。

### 3.3 图二：视觉风格图

图二可以是完整 UI、局部组件、材质板、游戏截图或概念图。读取时必须提取：

- 主色、辅色、警示色和明度层级；
- 边框厚度、层数、倒角、圆角或切角语言；
- 材质类型和表面细节；
- 磨损、划痕、污渍、锈蚀和装饰密度；
- 高光、阴影、环境光和内凹深度；
- 按钮、面板、槽位之间的视觉层级；
- 哪些内容属于风格，哪些只是该参考图的业务内容或布局。

风格迁移规则：

- 只迁移图二的视觉语言，不复制其文字、数字、图标、物品、业务内容或水印；
- 不复制图二中与图一冲突的尺寸、面板位置和分栏；
- 图二存在多种风格时，必须说明主参考与次参考；主参考决定整体风格，次参考只能补充指定细节；
- 无法同时满足多个风格参考时，将冲突项标记 `Pending`，不得无提示混合。

### 3.4 输入完整性与缺失处理

| 输入状态 | 处理方式 |
|---|---|
| 图一和图二齐全 | 按标准双参考流程执行 |
| 只有图一 | 可以整理布局和拆分清单；生成最终视觉前需确认风格，或明确采用项目既有风格 |
| 只有图二 | 可以提取风格语言；生成完整 UI 前需确认布局，不能直接照搬参考图布局 |
| 图一与图二冲突 | 图一的结构和布局优先，图二仅提供视觉风格 |
| 多张图一 | 明确主排布图；其他图仅补充状态、尺寸或局部结构 |
| 多张图二 | 明确主风格图及每张次参考负责的细节 |
| 输入边界模糊 | 建立候选区域清单，标记 `Pending`，确认后生成 |

任务开始前必须记录：

## 4. 核心定义 / Non-Negotiable Definitions

### 4.1 一个文件只承担一个职责

```text
一个 PNG = 一个完整按钮
或
一个 PNG = 一个完整图标/槽位
或
一个 PNG = 一个独立状态效果
或
一个 PNG = 一张结构模板
```

单个组件 PNG 禁止包含：

- 公共面板背景；
- 相邻组件；
- 原界面截图区域；
- 与组件无关的黑色矩形底；
- 动态数字；
- 普通说明文字；
- 需要本地化的文本。

### 4.2 裁切不等于抠图

`裁切 / crop` 只缩小矩形画布。  
`抠图 / cutout` 必须沿组件真实轮廓建立 Alpha。

```text
组件真实轮廓内：保留
组件真实轮廓外：Alpha = 0
```

以下情况不算完成抠图：

- 只把矩形四角设为透明；
- 保留周围公共背景；
- 用黑、白、绿色背景代替透明；
- 在深色看图器里“看起来透明”；
- 使用圆角或斜角遮罩，但遮罩内部仍含无关背景。

Cropping is not extraction. Black is not transparency. Pixels outside the real component silhouette must have alpha `0`.

### 4.3 模板也必须透明

最终纯净模板保留完整 UI 结构本体，但 UI 外框之外必须透明。

## 5. 元素分类 / Component Classification

修改任何像素前，必须先将元素分为：

1. 背景；
2. 结构面板；
3. 可交互按钮；
4. 图标或槽位；
5. 滑轨、滑块头、进度底图和填充；
6. 卡片和状态效果；
7. 按钮识别必需的特殊字符；
8. 按钮识别必需的动作词；
9. 普通文字；
10. 动态文字、价格、数量和比例；
11. 动画或粒子效果。

不确定元素是否独立时，先保持独立，禁止直接烘焙进结构模板。

### 5.1 文字保留规则

只有同时满足以下条件，文字才可以随按钮保留：

- 属于按钮身份的核心动作词或符号；
- 不会动态变化；
- 不需要本地化；
- 项目明确要求烘焙；
- 字体、描边和效果属于按钮美术的一部分。

可保留示例：

- `×`
- `?`
- “确认”
- “领取”
- “开始锻造”

必须删除或独立：

- 数量、价格、倒计时、进度，例如 `0/0`、`1/5`、`200`；
- 页面标题；
- 属性说明；
- 步骤提示；
- 描述文本；
- 玩家名称；
- 可配置或需本地化的文字。

默认策略：不确定时将文字独立，不烘焙。

## 6. 强制制作顺序 / Mandatory Workflow

```text
1. 读取 README、INTRODUCTION 和配置资料
2. 确认 `ProjectDisplayName`、`ProjectId` 和 `ComponentPrefix`
3. 创建以 `ProjectId` 命名的项目根目录
4. 枚举并查看全部输入图
5. 明确图一 `LayoutReference`、图二 `StyleReference` 以及其他拆分来源
6. 从图一记录画布、比例、区域、位置、层级、嵌套和空白约束
7. 从图二提取材质、配色、边框、光影、磨损和装饰语言
8. 检查双参考是否缺失或冲突；结构冲突时以图一为准
9. 记录目标平台、格式、目录、文字策略和是否需要重组
10. 预判所有元素职责并建立候选区域清单
11. 按 `PanelSelectionMode` 确认本次生成的面板 ID、位置、职责和嵌套组件
12. 建立正式拆分清单并记录 Include、Exclude 和 Pending
13. 严格按图一布局、图二风格生成或整理完整效果图
14. 检查图一中的空白区域是否被错误加入分栏、槽位、按钮或文字
15. 先提取按钮、图标和独立状态效果
16. 每个组件单独隔离
17. 建立真实透明 Alpha
18. 清理低 Alpha 背景残留并按实体边框极限裁剪
19. 制作按钮和交互状态
20. 从完整效果图移除已提取的按钮与图标并修复底纹
21. 保存无按钮/无图标、仍有普通文字的中间模板
22. 从中间模板移除普通文字和动态内容
23. 保存最终纯净透明模板
24. 从最终模板拆分已确认的结构面板
25. 按原坐标、锚点、层级和裁剪偏移重新组合
26. 执行第一轮数据与视觉 QA，并分别对照图一布局和图二风格
27. 更新 README、INTRODUCTION、选择记录和正式清单
28. 重新读取目录与输入资料，执行独立第二轮复核
```

禁止：

- 先无差别去字，再尝试恢复按钮符号；
- 未分类就开始裁切；
- 从带字效果图直接拆结构面板；
- 用图二的布局覆盖图一；
- 把图一的占位颜色当作最终风格；
- 在图一明确为空的区域擅自增加内部结构；
- 未完成面板选择确认就生成范围不明确的资源；
- 把截图矩形当作组件；
- 把候选文件直接写入 `out`；
- 只修改文件而不更新文档；
- 只更新文档而不核对真实目录。

## 8. 真透明抠图 / True-Alpha Extraction

### 8.1 隔离

- 每次只处理一个组件；
- 不带入相邻组件；
- 不带入公共面板；
- 键色必须与组件颜色明显不同；
- 键色背景必须均匀，无阴影、渐变、纹理或反射。

复杂透明对象如玻璃、烟雾、毛发、半透明光效，应使用支持原生透明的工作流或人工蒙版，不强行使用简单键色。

### 8.2 Alpha 转换

- 键色区域转换为 Alpha `0`；
- 实心区域应接近 Alpha `255`；
- 抗锯齿边缘允许合理半透明；
- 必须去除键色色溢；
- 不得误删主体内部的暗色、孔洞或反射。

### 8.3 通用紧边裁剪与标准画布

本节适用于任意分辨率、宽高比、平台和资源类型，包括横屏、竖屏、超宽屏、高分屏、按钮、图标、槽位、面板、模板、状态效果、滑块、进度条和特殊美术字。不得写死某个任务的像素尺寸、坐标或比例。

统一处理顺序：

1. 先确定当前资源的合法目标范围 `Target Region`。目标范围来自白模、组件清单、配置、原始坐标或人工确认，不得默认使用整张截图；
2. 只在 `Target Region` 内处理像素，范围外内容一律不属于该资源；
3. 完成抠图和 Alpha 清理后，以 `Alpha > 0` 的全部有效像素计算非透明包围盒 `Visible Bounds`；
4. `Visible Bounds` 必须包含主体、抗锯齿边缘以及属于该资源的阴影、描边、外发光和粒子边缘；
5. 将 `Visible Bounds` 之外的透明像素裁掉，生成正式画布；
6. 最终文件名中的 `WidthxHeight` 必须等于裁剪后文件的真实像素尺寸；
7. 保存裁剪偏移量 `CropOffset = VisibleBounds.Min - TargetRegion.Min`，用于锚点、九宫格、点击区和原位重组。

通用规则：

- 单个静态组件默认按自身 `Visible Bounds` 紧边裁剪，不得保留原截图尺寸、目标范围外透明区域或无意义的大面积透明留白；
- 不得直接把键色转换后所有 `Alpha > 0` 的像素都视为有效内容。键色噪声、压缩污染和肉眼不可见的低 Alpha 残留必须先清除，否则会错误扩大包围盒；
- 对具有清晰实体边框的面板、按钮、槽位和图标，应使用高置信实体像素确定最外边界，再向内保留原有抗锯齿；正式画布边缘应与最外层实体边框相接，不得在边框之外额外添加透明安全边；
- Alpha 阈值不得写死为全项目常量。应根据源图压缩、边缘半透明和材质特性确定，并同时检查实体包围盒、低 Alpha 残留包围盒和肉眼可见边缘；
- 极限裁剪后必须验证：非透明内容包围盒覆盖正式画布边界，或仅在真实斜角、圆角、孔洞等轮廓位置出现必要透明角；不得因“四角透明”要求人为增加整圈透明底；
- 同一交互状态组不得分别紧边后造成跳动。必须先计算所有状态的 Alpha 包围盒，再取联合包围盒 `Union Bounds`，所有状态使用相同画布尺寸、主体位置、锚点和 `CropOffset`；
- 完整模板按 UI 结构本体的外轮廓紧边裁剪；模板内部为布局保留的透明区域可以存在，但模板外轮廓之外不得保留透明画布；
- 阴影、描边、外发光和粒子属于组件时必须计入包围盒；与组件无关的环境阴影、截图背景和场景光效必须删除；
- 九宫格资源紧边裁剪后必须同步换算边界值；若裁剪导致安全拉伸区失效，则扩大到满足九宫格所需的最小画布，并记录原因；
- 对齐或动画确实需要固定画布时，只能使用由状态组联合包围盒、骨骼范围、动画最大运动范围或配置明确规定的标准画布，禁止无依据沿用整张源图；
- “保留原坐标的重组预览”只能存放在 `into/ReassemblyPreview`，不得代替 `out` 中的正式资源；
- 任何尺寸、比例和类型都执行同一算法，不得为某个分辨率建立隐藏特例。

### 8.4 透明验收

每张 PNG 必须满足：

- 包含真实 Alpha 通道；不规则轮廓必须同时存在透明与非透明像素，完全覆盖矩形画布的直角实体资源允许 Alpha 全为 `255`；
- 非透明包围盒非空；
- 已记录 `Target Region`、`Visible Bounds`、裁剪后尺寸和 `CropOffset`；
- 单组件已按自身包围盒紧边裁剪；状态组已按联合包围盒统一裁剪；
- 无目标范围外透明画布和无意义透明留白；
- 四角 Alpha 按真实轮廓验收：斜角、圆角和不规则轮廓应为 `0`；直角实体边框允许非零，禁止为了让四角为 `0` 而增加透明画布；
- 组件外无黑底、白底或键色；
- 残留键色像素为 `0`；
- 100% 整体检查通过；
- 400% 边缘检查通过；
- 棋盘格预览通过。

## 10. 组件拆分规则 / Component Rules

### 10.1 面板

- 面板只保留结构；
- 关闭按钮、标题、图标、文字、滑块和状态效果必须独立；
- 可拉伸面板需要记录九宫格安全边距；
- 避免在面板中烘焙动态内容。

#### 10.1.1 大型复合面板的结构分区

当一个完整 UI 在移除小按钮、图标、文字和动态内容后，仍包含多个大型视觉区域时，不得把整个截图作为一个面板交付，也不得只按标注矩形机械裁切。必须根据结构语义拆成多个职责单一的大面板。

分区依据按优先级判断：

1. 独立闭合边框或连续金属框；
2. 独立底纹、材质、颜色或明暗层级；
3. 明确的布局职责，例如左侧导航区、右上主内容区、右下控制区；
4. 独立九宫格拉伸需求；
5. 独立显示、隐藏、替换、缩放或动画需求；
6. 程序层级、预制体、配置或交互作用域。

满足以下任一条件时，应优先拆为独立大面板：

- 区域拥有完整或可合理补全的四边框；
- 区域可在不破坏相邻区域的情况下独立显示或替换；
- 区域与相邻区域使用不同的九宫格安全区；
- 区域在程序中属于不同容器、滚动区、标签页或控制区；
- 区域的尺寸、锚点或适配策略与相邻区域不同。

不得作为独立大面板的情况：

- 仅有一条装饰线、投影或高光，没有独立结构职责；
- 只是公共父面板上的颜色变化；
- 拆出后无法形成完整边界，且没有配置或程序层级支持；
- 只是按钮、卡片、槽位、图标或状态效果，应按对应组件类型拆分；
- 标注框覆盖多个结构，仅用于说明关注范围而非真实组件轮廓。

#### 10.1.2 拆分顺序

```text
完整 UI
→ 识别并提取按钮、图标、文字、动态内容和状态效果
→ 修复它们移除后留下的底纹与边框
→ 得到纯结构母版
→ 识别大型闭合结构区域
→ 建立区域邻接与层级关系
→ 分配共享边界的唯一归属
→ 分别抠出各大型面板
→ 按各自 Alpha 包围盒紧边裁剪
→ 记录坐标、裁剪偏移、锚点和九宫格
→ 原位重组并与纯结构母版比较
```

禁止直接从仍含按钮、图标、文字、彩色标注线或动态内容的截图裁出正式大面板。

#### 10.1.3 共享边界与重叠区域

- 两个大面板相接时，必须指定接缝、分隔条、压边或阴影的唯一资源归属；
- 同一条实体边框不得在两个正式面板中重复烘焙，否则重组后会加粗、变亮或产生双影；
- 上层压边归属于视觉上覆盖下层的面板；公共分隔条若需要独立控制，应单独拆为 `Divider`；
- 为避免抗锯齿裂缝，可在中间处理阶段保留少量安全重叠，但正式资源必须通过原位重组确认无重边、漏缝和亮线；
- 标注圈、手绘框和辅助颜色仅用于表达区域，不属于任何资源，必须在正式拆分前清除；
- 无法确定接缝归属时，不得猜测，应在拆分清单中标记 `Pending` 并通过层级或重组测试确认。

#### 10.1.4 大面板拆分清单

每个大面板除通用清单字段外，还必须记录：

| 字段 | 说明 |
|---|---|
| ParentPanel | 所属纯结构母版 |
| RegionRole | 区域职责，例如导航、主内容、控制区 |
| StructuralBoundary | 闭合边框或结构边界的判定依据 |
| AdjacentPanels | 相邻面板及方位 |
| SharedEdgeOwner | 共享接缝、压边或分隔条的唯一归属 |
| ZOrder | 重组层级 |
| ReassemblyPosition | 相对母版的原始坐标 |
| NineSliceInsets | 九宫格安全边距或 `Not Applicable` |

#### 10.1.5 生成前可选面板确认

每次进行面板生成、抠图或拆分前，应先执行一次“面板选择确认”。该步骤用于确定本次实际需要处理哪些区域，避免漏扣嵌套组件，也避免生成用户不需要的面板。

确认模式为可选项：

```text
PanelSelectionMode:
- ConfirmSelection：先列出候选面板，由用户选择后生成；推荐默认值
- AllDetected：生成所有检测到且边界明确的面板
- ExplicitOnly：只生成用户明确点名的面板
```

如果用户已经明确指定了区域，可直接按 `ExplicitOnly` 执行，不重复询问。若用户只说“拆面板”但未指定范围，则应使用 `ConfirmSelection`，先给出候选清单再生成。

候选面板必须同时使用“唯一 ID + 相对位置 + 结构职责”描述，不能只说“这个”“那个”或只依赖标注颜色。

推荐位置词：

```text
TopLeft       左上角
TopCenter     上方中央
TopRight      右上角
MiddleLeft    左侧中部
Center        中央
MiddleRight   右侧中部
BottomLeft    左下角
BottomCenter  下方中央
BottomRight   右下角
LeftSidebar   左侧栏
RightSidebar  右侧栏
Header        顶部栏
Footer        底部栏
Overlay       浮层
Nested        嵌套在其他面板内
```

位置描述规则：

- 位置以目标 UI 自身边界为坐标参考，不以整张截图、设备屏幕或透明画布为参考；
- 使用归一化中心点辅助判断：`x < 0.33` 为左，`0.33–0.66` 为中，`x > 0.66` 为右；`y < 0.33` 为上，`0.33–0.66` 为中，`y > 0.66` 为下；
- 侧栏、顶部栏和底部栏等具有明确布局职责的区域，优先使用职责词而不是角落词；
- 位于另一面板内部的小面板、按钮或槽位必须标记 `Nested`，同时写明父面板 ID；
- 标注颜色只能作为辅助描述，例如“红框区域”，不得替代位置、职责和唯一 ID；
- 同一位置存在多个组件时，增加层级、大小或顺序描述，例如 `TopLeft_OuterPanel`、`TopLeft_InnerButton`。

候选清单格式：

| Select | ID | Position | RegionRole | Parent | BoundaryStatus | Description |
|---|---|---|---|---|---|---|
| `[ ]` | P01 | LeftSidebar | 导航面板 | Root | Confirmed | 左侧纵向大框 |
| `[ ]` | P02 | TopRight | 主内容面板 | Root | Confirmed | 右上大型内容框 |
| `[ ]` | P03 | BottomRight | 控制面板 | Root | Confirmed | 右下横向控制框 |
| `[ ]` | C01 | Nested / TopLeft | 黄色按钮面板 | P01 | Confirmed | 左侧面板内部的黄色横向组件 |

选择状态：

```text
Include  本次生成
Exclude  本次不生成
Pending  边界或职责不明确，确认前不得正式生成
```

确认时至少说明：

1. 本次采用的 `PanelSelectionMode`；
2. 将生成的面板 ID、位置和职责；
3. 明确排除的区域；
4. 嵌套组件是否单独生成；
5. 标注线、文字、图标、按钮和动态内容的处理方式；
6. 是否同时生成纯结构母版和重组预览。

用户确认后的选择结果必须写入拆分清单。生成过程中发现新的嵌套组件或边界冲突时，应暂停该组件的正式导出，将其标记为 `Pending`，并补充确认；不得静默遗漏或擅自合并。

大型面板拆分完成后，必须同时交付：

- 每个大面板的真透明紧边 PNG；
- 无按钮、无图标、无文字的纯结构母版；
- 原位重组预览；
- 面板分区清单；
- 重边、漏缝和透明度检查结果。

### 10.2 按钮

#### 10.2.1 强制状态组

```text
Normal
Hover
Pressed
Disabled
```

除非目标平台或交互设计明确声明某状态不适用，每个可交互按钮必须交付以上四个独立 PNG。四态不是建议项，也不是后续可选优化，而是正式交付硬门槛。

状态职责：

| State | 含义 | 最低视觉要求 |
|---|---|---|
| Normal | 默认可交互状态 | 作为视觉和位置基准 |
| Hover | 指针悬停状态 | 在不改变轮廓和位置的前提下略亮、增强边缘或产生克制高光 |
| Pressed | 按下状态 | 略暗、内凹、轻微下压或改变高光方向，但点击热区和锚点不变 |
| Disabled | 禁用状态 | 降低饱和度、亮度和对比度，但仍可识别按钮身份 |

强制要求：

- 画布、Alpha 轮廓、主体位置和锚点一致；
- 状态切换不得跳动；
- 四态必须以同一 `Normal` 母件为基准生成，不得分别自由重画成不同结构；
- 先计算四态联合包围盒 `Union Bounds`，再把所有状态放入相同画布；
- 文件名中的组件名和 `WidthxHeight` 必须完全一致，只允许 `State` 字段变化；
- 按钮核心动作符号或经批准烘焙的动作词必须在四态中保持一致；
- 不得在 Hover、Pressed 或 Disabled 中引入新文字、动态图标、公共背景或相邻组件；
- 必须制作四态并排对比图，并执行逐像素尺寸、锚点和主体中心检查；
- 必须实际执行至少一次 `Normal → Hover → Pressed → Normal → Disabled` 切换检查。

#### 10.2.2 不适用状态

只有存在明确平台或产品依据时，状态才可以标记 `Not Applicable`：

- 纯触屏界面通常可以将 Hover 标记为 `Not Applicable`；
- 永不进入禁用逻辑的按钮可以将 Disabled 标记为 `Not Applicable`，但必须由产品或配置确认；
- 非交互装饰件不是按钮，应重新分类，不能用 `Not Applicable` 规避状态制作；
- Normal 和 Pressed 对可点击按钮默认不可省略。

每个不适用状态必须在 README、INTRODUCTION、拆分清单和 QA 中记录：

```text
Component:
State:
Result: Not Applicable
Reason:
Evidence:
```

不得使用“暂未制作”“以后补充”“当前只有 Normal”“本轮先做基准版”等说法代替 `Not Applicable`。缺少必需状态只能判定为 `Pending` 或 `Fail`。

#### 10.2.3 正式目录门槛

- 四态未完成或未获准标记 `Not Applicable` 时，该按钮组只能存放在 `into/Candidates`；
- 不完整按钮组不得写入 `out/Components`；
- 只有 Normal 的资源不得命名、描述或汇报为最终版、正式版、完成版或通过；
- 已有 Normal 正式文件但发现状态缺失时，必须将整组移出 `out`，补齐并通过 QA 后再整体写回；
- 同一按钮组必须整体晋级到 `out`，禁止单个状态先行成为正式资源。

#### 10.2.4 状态组清单

每个按钮必须记录：

| Component | Normal | Hover | Pressed | Disabled | Canvas | Anchor | Result |
|---|---|---|---|---|---|---|---|
| ExampleButton | Pass | Pass | Pass | Pass | Same | Same | Pass |

`Result` 判定：

- 所有必需状态为 `Pass`，其余状态有有效 `Not Applicable` 记录：`Pass`；
- 任一必需状态未生成或未验证：`Pending`；
- 任一状态尺寸、位置、轮廓、锚点或职责不一致：`Fail`。

### 10.3 滑块和进度条

必须分开：

- Track；
- Handle；
- Background；
- Fill；
- Endpoint decoration。

必须测试最左、中间、最右位置，确认无轨道缺口、底色残留或端点错位。

### 10.4 卡片和槽位

- 卡片底框与内容分离；
- 选中、警告、缺失、完成等效果独立；
- 图标、数量、品质角标和锁定标记独立；
- 同类卡片保持相同画布和锚点。

### 10.5 文字和数字

- 普通文字默认使用引擎文本节点；
- 动态数字必须独立；
- 不得把 `0/0`、价格、倒计时等烘焙进槽位；
- 需要特殊美术字时，也应作为独立透明资源。

## 11. 通用与专用 / Shared vs Module-Specific

每个资源必须标记复用范围：

- `Shared`：全项目可复用；
- `ModuleSpecific`：只属于当前功能界面。

判断原则：

- 关闭按钮、标准滑轨、通用品质框可能是 Shared；
- 主面板、业务专用按钮、特殊槽位通常是 ModuleSpecific；
- 不确定时先按 ModuleSpecific，避免错误复用；
- 已被代码、配置或预制体引用的资源名属于接口，改名前必须核对引用。

## 17. 常见失败 / Common Failures

### 把截图当抠图

表现：组件周围带有原面板。  
修复：单组件隔离、键色或蒙版转 Alpha、棋盘格检查。

### 把黑底当透明

表现：PNG 有黑色背景但无有效透明区域。  
修复：读取 Alpha 数据，确认最小值为 `0`、四角为 `0`。

### 无差别去字

表现：按钮识别符号或动作词被删除。  
修复：去字前完成文字分类；只清除普通和动态文字。

### 动态数字烘焙

表现：槽位、卡片或按钮包含 `0/0`、价格、倒计时。  
修复：数字改为独立文本层。

### 错把普通行当按钮

表现：整条说明区域被错误导出为按钮。  
修复：检查是否存在点击行为、状态变化、独立边框和程序职责。

### 面板混入交互件

表现：结构底图仍含关闭按钮、图标、滑块或文字。  
修复：重新执行两级模板流程。

### 文档与目录不一致

表现：README 列出不存在文件或遗漏现有文件。  
修复：重新枚举真实目录后生成清单，禁止凭记忆修改。

# 20. 按钮内部不透明规则 / Solid Button Interior

本规则适用于普通文字按钮、标签按钮、图标按钮、关闭按钮及其全部交互状态。

- 按钮必须作为完整的实心 UI 板件导出，不能只保留边框、文字或符号。
- 按钮外轮廓之外必须为透明区域；按钮外轮廓以内的边框、底板和纹理必须完整保留。
- 非符号类按钮只去除文字，不得把文字下方的底板或纹理同时抠除。
- 符号类按钮保留识别符号，同时必须保留符号背后的完整按钮底面。
- 禁止对按钮直接使用会穿透面板内部的全图差分 Alpha 蒙版。
- `Normal`、`Hover`、`Pressed`、`Disabled` 必须使用相同画布、相同外轮廓、相同主体位置和相同锚点。
- 每次导出必须检查按钮中心点及内部安全区域，Alpha 必须为 `255`。
- Alpha 为 `0` 的像素只允许出现在按钮外轮廓之外的角部、镂空结构定义区域或阴影外侧。
- 在透明棋盘格检查中，只要棋盘格从按钮面板内部透出，本轮 QA 必须判定为失败；修复后重新导出、重新回拼并再次检查。

交付前确认：

```text
按钮内部是否保持完整实心？
按钮中心点和内部安全区 Alpha 是否为 255？
透明像素是否只存在于按钮外轮廓之外？
去字后是否正确补全了按钮底板与纹理？
符号按钮是否同时保留了符号和完整底面？
四态按钮是否使用完全一致的画布与锚点？
```
